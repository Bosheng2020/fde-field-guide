# 岗位地图：FDE 与相邻职能

**语言：** [English](../en/02-role-map.md) · 简体中文  
**内容类型：** 参考官方岗位说明后的作者总结  
**最后检查：** 2026-10-22

职位名称并不可靠，责任边界更有意义。下表描述常见的工作重心，而不是统一规则。

| 岗位 | 首要问题 | 常见产出 | 常见交付边界 |
|---|---|---|---|
| 软件工程师 | 如何构建并维护产品？ | 产品能力与代码 | 能力发布 |
| ML / 研究工程师 | 如何改善模型或 ML 系统行为？ | 模型、数据、实验、基础设施 | 达到研究或生产标准 |
| 售前工程师 | 产品能否解决潜在客户的问题？ | Demo、价值验证、技术验证 | 商业机会进入下一阶段 |
| 解决方案架构师 | 什么架构能让方案成立？ | 目标架构与计划 | 设计被接受 |
| 实施工程师 | 如何配置和集成已定义范围？ | 完成配置的集成 | 约定范围完成 |
| 咨询顾问 | 组织应该改变什么？ | 分析、建议、转型方案 | 建议完成移交 |
| 产品经理 | 产品应该规模化解决什么？ | 优先级、需求、产品决策 | 团队执行路线图 |
| 客户成功 | 客户如何持续获得价值？ | 采用计划、健康度、续约/扩展信号 | 关系持续运营 |
| **FDE** | 如何把模糊问题变成被采用的生产结果？ | 端到端系统、证据、可复用经验 | 结果进入运营，经验反馈产品 |

## 不同公司的运行模式并不相同

同一个名称可能对应不同组合：

- **产品驱动部署：** 把成熟平台适配到复杂环境；
- **任务驱动构建：** 深入关键业务，并围绕真实操作构建软件；
- **前沿模型部署：** 围绕快速变化的 AI 能力构建系统和评估；
- **行业部署：** 将工程与医疗、金融、法律、政府等领域知识结合；
- **开发者工作流部署：** 改变工程团队构建软件的方式，并留下可持续习惯。

官方职位说明展现了这种差异：

- **OpenAI：** 前沿模型端到端部署、生产采用、工作流影响，以及改变产品和模型路线图的反馈；
- **Palantir：** 软件、基础设施、可靠性和安全等多类 Forward-Deployed 工程岗位，通常与 Deployment Strategist 配合；
- **Scale AI：** 覆盖客户环境、AI 应用、数据集成、生产运营和平台反馈；
- **Cursor：** 深入客户工程团队，构建生产级工作流、推动采用，并把可持续方法留在客户组织中。

## 用类似 RACI 的方式检查边界

每个项目都应明确谁对以下事项负责：

| 决策 / 产物 | FDE 默认责任 | 必须配合的负责人 |
|---|---|---|
| 问题定义和成功标准 | 负责或共同负责 | 客户工作流负责人 |
| 架构和最小完整切片 | 负责 | 客户工程/安全团队 |
| 核心产品修改 | 参与 | 产品/核心工程负责人 |
| 评估验收标准 | 共同负责 | 领域专家和风险负责人 |
| 生产访问审批 | 参与 | 客户安全/平台负责人 |
| 用户采用和培训 | 共同负责 | 业务负责人/内部推动者 |
| 移交后的事故责任 | 明确约定 | 运营团队 |
| 商业条款 | 知情/参与 | 商务负责人 |

如果所有事项都悄悄落到 FDE 身上，项目治理通常不完整；如果 FDE 对任何事项都不负责，那么这个角色更像顾问，而不是结果负责人。

## 健康的边界

出现以下情况时，FDE 应拒绝或重新谈判范围：

- 客户无法指定工作流负责人；
- 成功无法观察或衡量；
- 生产风险没有明确审批者；
- 项目实质是无限期人力外包；
- 一次性需求会损害核心产品，却没有战略学习价值；
- “紧急”被用来掩盖不可接受的安全或可靠性风险。

## 常见团队结构

一个典型小组可能包括：

- **FDE：** 技术交付和端到端集成；
- **部署 / 业务负责人：** 管理层协调、领域价值和项目推进；
- **产品 / 研究伙伴：** 可复用的产品和模型改进；
- **客户负责人：** 访问权限、决策、采用和运营；
- **安全 / GRC：** 风险接受和控制设计。

小公司可能由一个人覆盖多个角色，但每项责任仍应有明确负责人。
