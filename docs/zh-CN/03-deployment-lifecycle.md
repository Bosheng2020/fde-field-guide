# Forward Deployed Engineering 生命周期：从需求发现到生产采用

**语言：** [English](../en/03-deployment-lifecycle.md) · 简体中文  
**内容类型：** 实战手册  
**最后检查：** 2026-10-22

生命周期需要反复迭代。各阶段是决策门，并不意味着需求发现结束后才能开始工程工作。

| 阶段 | 关键决策 | 最低产物 | 退出证据 |
|---|---|---|---|
| 0. 筛选 | 是否值得且足够安全地探索？ | 机会简报 | 发起人、潜在价值、访问路径 |
| 1. 发现 | 当前工作到底如何进行？ | 工作流地图 | 用户、决策、例外、基线 |
| 2. 定义 | 我们具体对什么结果负责？ | 结果约定 | 范围、指标、失败边界、非目标 |
| 3. 观测 | 如何评估现实表现？ | 评估与监控计划 | 代表性案例和验收规则 |
| 4. 构建 | 最小完整切片能否运行？ | 集成后的垂直切片 | 真实数据/工具、控制和追踪 |
| 5. 试点 | 在受控真实使用中是否有效？ | 试点报告 | 任务质量、反馈、错误分类 |
| 6. 强化 | 能否安全、重复地运营？ | 生产就绪评审 | 安全、可靠性、运行手册、回滚 |
| 7. 上线 | 工作流能否形成持续采用？ | 推广计划 | 负责人、培训、监控、支持 |
| 8. 扩大 / 停止 | 是否应扩大范围？ | 结果复盘 | 价值、成本、风险、采用趋势 |
| 9. 提炼 | 什么可以复用？ | 一线学习简报 | 产品变化、评估、组件、手册 |

## 0. 筛选机会

寻找有意义的工作流、明确发起人、可接触的用户、可访问的数据或工具，以及能够观察的结果。如果项目唯一目标只是“使用 AI”，或者法律与安全条件让安全实验都不可能，应及时拒绝。

## 1. 发现真实工作流

观察用户，而不是只听管理层描述。梳理触发条件、参与者、决策、系统、交接、队列、例外、审批路径和失败成本。即使不完美，也要建立当前基线。

常用方法：

- 跟随观察和实际产物走查；
- “给我看最近三个真实案例”的访谈；
- 例外与升级记录复盘；
- 流程和数据血缘图；
- 利益相关者与激励关系图。

## 2. 建立结果约定

明确：

- 目标用户和工作流步骤；
- 当前基线和期望变化；
- 范围内与范围外行为；
- 不可接受的失败；
- 自主程度和人工审批边界；
- 负责人、决策节奏和目标日期；
- 扩大、暂停或停止的条件。

它不是法律合同，而是一份共同决策工具。

## 3. 扩大之前先建立观测

在优化 Demo 前建立代表性评估集，覆盖常见任务、高价值案例、关键边界情况和不可接受的失败。同时定义产品与商业指标，而不仅是模型指标。

## 4. 构建最小完整切片

在真实环境中完成一条最小但完整的路径：身份、数据、模型、工具、界面、验证、日志和人工控制。探索阶段可以使用模拟，但应尽早替换风险最高的假设。

## 5. 用受控用户试点

选择能够代表工作流的投入型用户，而不只是技术爱好者。保留与原有基线的比较，记录修正、覆盖操作、延迟、成本、困惑，以及用户在哪一步离开系统。

## 6. 强化为生产系统

生产就绪评审至少覆盖：

- 身份、权限、隐私、保留策略和审计；
- 负载、延迟、可用性、速率限制和成本；
- 重试、幂等、降级、超时和回滚；
- 评估回归、版本和变更控制；
- 支持责任、事故级别和升级路径。

## 7. 进入真实运营方式

部署也是一次变革管理。培训用户何时可以信任、何时需要核验、如何覆盖以及如何升级。让管理者看到效果，同时避免形成监控员工的工具。FDE 退出前必须明确后续运营负责人。

## 8. 扩大、重构或停止

扩大范围需要由证据赢得。把价值、使用、质量、成本和风险与最初基线比较。稳定模式可以扩大；有潜力但被阻塞的流程需要重构；证据无法支持投资时应停止。

## 9. 提炼一线经验

把故事转化为资产：

```mermaid
flowchart LR
    A[观察到的失败] --> B[可重复 Trace]
    B --> C[带标签的评估案例]
    C --> D[系统或模型修改]
    D --> E[回归测试]
    E --> F[生产结果]
    F --> G[产品 / 研究 Backlog]
```

可以直接使用[一线信号模板](../../templates/field-signal.zh-CN.md)与[部署复盘模板](../../templates/deployment-review.zh-CN.md)。
