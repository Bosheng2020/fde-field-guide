# 安全、治理与生产风险

**语言：** [English](../en/07-security-governance.md) · 简体中文  
**内容类型：** 面向风险的工程指南  
**最后检查：** 2026-10-22

安全不是原型完成后追加的清单。它决定系统可以看到哪些数据、执行哪些动作、如何保留证据，以及什么自主程度有合理依据。

## 从后果开始

按照以下维度给每项动作分类：

- **影响：** 可能发生什么错误，会影响谁；
- **可逆性：** 结果能否撤销；
- **可检测性：** 错误动作多久能被发现；
- **范围：** 一条记录、一个租户，还是大量系统/用户；
- **权限：** 哪个身份和权限允许执行；
- **证据：** 该行为在真实条件下经过了多充分的测试。

后果越严重，权限越应狭窄，验证越应严格，审批越应明确，监控越应完善，自主扩展越应缓慢。

## 对完整系统做威胁建模

至少考虑：

- 恶意或无意的用户输入；
- 文档、网页、邮件或工具输出中的间接 Prompt Injection；
- 被攻破或权限过大的集成；
- 跨租户或跨用户数据泄露；
- Prompt、日志、Trace 或生成代码中的 Secret 泄露；
- 不安全代码执行和网络访问；
- 未授权工具调用或被操纵的参数；
- 模型或依赖变化；
- 被污染的检索源和过期数据；
- 内部人员滥用和过大的支持权限；
- Token、工具或循环失控导致的成本攻击；
- 技术检查通过、但会误导真实决策的输出。

## 控制层

### 身份与授权

- 验证发起工作的人员或服务；
- 对每次数据访问和工具动作授权，而不只是允许进入应用；
- 在检索和执行全过程传递租户与用户身份；
- 使用最小权限、短期凭据，并分离读写工具；
- 不允许模型给自己增加权限。

### 输入与上下文

- 把可信指令与不可信内容明确分离；
- 限制和清理外部内容，同时保留来源；
- 把检索文本和工具输出视为数据，而不是可执行策略；
- 强制约束使用白名单和确定性程序执行。

### 输出与行动

- 用 Schema 和业务规则验证结构化输出；
- 高影响动作先预览，并要求正确的审批者；
- 使用幂等键、事务边界和限额；
- 沙箱化代码或文件操作，并限制网络目标；
- 把安全拒绝和人工升级设计成一等结果。

### 数据与隐私

- 记录目的、来源、分类、驻留、保留和删除方式；
- 尽量减少发送给模型和观测系统的数据；
- 不需要完整文本时，对敏感值脱敏或 Tokenize；
- 测试删除、权限撤销和租户隔离。

### 运营

- 版本化模型、Prompt、工具、策略和评估集；
- 保留调查人员能够理解的审计链；
- 监控权限错误、异常动作、成本激增、循环和策略违规；
- 准备回滚、Kill Switch、降级模式和事故联系人。

## 基于风险的自主升级门槛

提高自主程度之前，回答：

1. 动作能否撤销？
2. 能否在造成伤害前可靠检测错误行为？
3. 权限是否限制在最小必要范围？
4. 评估集是否包含真实滥用和边界案例？
5. 是否有明确风险负责人接受剩余风险？
6. 运营团队能否立即停止系统？

任何一个答案为“否”，都应保留或增加人工审批。

## 治理产物

一个务实部署通常需要：

- 系统与数据流图；
- 数据清单和保留计划；
- 工具 / 权限清单；
- 威胁模型与滥用案例；
- 评估与红队结果；
- 模型 / 系统说明或部署事实表；
- 有明确审批人的生产就绪决策；
- 事故、回滚和沟通手册；
- 变更日志和定期权限复查。

治理应通过让证据可见来加速决策，而不是产生无人负责的文件。

## AI 行为事故响应

1. **控制：** 关闭动作、工具、模型路由或受影响租户；
2. **保全：** 保存脱敏 Trace、版本、审批和受影响记录；
3. **评估：** 确定严重度、范围、持续暴露和通知义务；
4. **修正：** 修改系统、数据、工具、策略或模型；
5. **回归：** 把失败加入保留测试和红队案例；
6. **学习：** 更新手册、权限、培训和产品设计。
