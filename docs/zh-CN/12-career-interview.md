# FDE 职业与面试指南

**语言：** [English](../en/12-career-interview.md) · 简体中文  
**内容类型：** 求职者与招聘者实战手册  
**最后检查：** 2026-10-22

FDE 面试往往同时考察传统软件面试中被分开的能力：工程深度、产品判断、客户需求发现、在模糊环境中执行，以及把技术决策连接到运营结果的能力。由于不同公司对岗位定义不同，应为真实责任范围准备，而不只是为 FDE 这个缩写准备。

## 首先确认岗位本身

询问这家公司所说的“Forward-Deployed”具体意味着什么：

- 团队是否负责需求发现、实施、生产运营、用户采用，还是全部？
- 多少内容进入核心产品，多少内容构建在客户环境中？
- 谁负责安全评审、支持和生产事故？
- 一线信号如何转化为产品路线图决策？
- 客户沟通、写代码、出差和内部协调分别占多少时间？
- 三个月、六个月和十二个月后的成功标准是什么？

这些问题有助于判断岗位究竟是结果导向的 FDE、实施、解决方案架构、售前，还是没有边界的定制开发。另见[岗位地图](02-role-map.md)。

## 建立有证据的作品集

不要只声称“我既懂技术又面向客户”。准备两到三个案例，展示从模糊问题到结果的完整路径。

每个案例至少记录：

1. **背景：** 用户、工作流、限制，以及问题为什么重要。
2. **基线：** 干预前如何工作，衡量了什么。
3. **你的决策：** 范围、架构、取舍，以及拒绝了什么。
4. **执行：** 代码、集成、评估、安全控制、上线和协作。
5. **失败：** 哪里出错、如何定位、后来改变了什么。
6. **结果：** 质量、采用、运营影响和仍存在的不确定性。
7. **复用：** 可复用组件、评估资产、手册或产品变化。

公开作品应使用合成数据、公开数据或获授权的数据。不要为了显得真实而泄露客户秘密。

### 一份有说服力的作品包

- 一页工作流与结果地图；
- 架构图与威胁/风险说明；
- 可运行应用或可重复仓库；
- 任务专用评估集与结果；
- Trace 或错误分类；
- 上线方案/运行手册节选；
- 说明下一步决策的简短部署复盘。

可以直接使用[需求发现画布](../../templates/discovery-canvas.zh-CN.md)、[评估计划](../../templates/evaluation-plan.zh-CN.md)、[架构与风险评审](../../templates/architecture-risk-review.zh-CN.md)和[部署复盘](../../templates/deployment-review.zh-CN.md)。

## 简历：写证据，而不是身份标签

一条有效经历可以采用以下结构：

> **负责** [用户/场景] 的 [工作流或结果]；**构建** [技术系统与集成]；在满足 [风险、成本、延迟或可靠性约束] 的同时，**改善** [可衡量结果]；并**沉淀** [可复用资产或产品洞察]。

建议写法：

- “梳理审核流程，构建带权限控制的检索与工具调用服务，引入任务级评估和分阶段上线，使经核验的处理时间降低 X%。”

避免：

- “利用最先进 AI 全面变革企业运营。”

只使用准确、可归属且有意义的数字。如果结果不能公开，不要编造精确数字，可以描述规模和证据，例如“目标运营团队每周持续使用”“通过客户生产就绪评审”或“将重复失败转化为回归测试”。

## 常见面试环节

| 环节 | 考察内容 | 强信号 |
|---|---|---|
| 编程 / 调试 | 能否在时间压力下实现和推理 | 清晰拆分、测试、边界情况、沟通 |
| 系统设计 | 能否设计完整、可运营的系统 | 需求、接口、失败模式、安全、观测、取舍 |
| AI / LLM 设计 | 能否构建超越 Demo 的系统 | 评估驱动、Grounding、工具控制、成本/延迟、人工边界 |
| 产品或部署 Case | 能否发现真正问题 | 工作流发现、基线、范围、分阶段证据、停止条件 |
| 客户角色扮演 | 能否建立信任而不夸大承诺 | 倾听、澄清、通俗解释、预期与冲突管理 |
| 行为经历深挖 | 是否真正负责过困难结果 | 具体决策、失败、责任、学习和可衡量结果 |
| 高管沟通 | 能否把技术细节连接到业务后果 | 简洁建议、选项、风险、证据、下一项决策 |

## 用 FIELD 组织 Case 回答

[FIELD 框架](10-field-framework.md)是 **Bosheng Ding 的原创总结**，可作为实用的答题结构。使用时应说明它是作者框架，而不是行业标准。

### Frame

澄清用户、工作流、基线、目标结果、发起人、限制、失败成本和非目标，并质疑是否真的需要 AI。

### Instrument

定义代表性案例、质量与安全标准、Trace、产品指标、业务指标和回滚信号。

### Engineer

提出最小完整垂直切片，覆盖数据、身份、模型、检索、工具、界面、验证、人工控制和最高风险假设。

### Launch

选择试点用户、上线阶段门、支持责任、用户培训、监控，以及提高自主程度或扩大范围的条件。

### Distill

解释如何把一线失败转化为评估、产品变化和可复用组件，并做出扩大、重构或停止决策。

该结构可以让回答始终围绕结果，而不是在理解问题之前就开始画架构图。

## 高频问题与回答信号

### “客户要求做一个 AI Agent，你首先做什么？”

好的回答会先调查当前工作流、真实案例、负责人、基线、限制和失败成本，再选择架构；同时提出有边界的需求发现计划，并接受“不应自动化”也可能是正确结论。

### “如何把原型推进到生产？”

应覆盖代表性评估、真实集成、权限、可观测性、失败处理、安全、Canary 上线、运行手册、用户培训、采用和回滚，并区分 Demo 效果与运营证据。

### “你会如何评估 Agent？”

定义任务单位、数据集及分组、确定性检查、经过校准的 Rubric/模型评估器、工具调用正确性、Trace 检查、安全失败、延迟、成本和在线结果指标；同时说明如何把失败转化为回归案例。

### “什么时候应该微调或后训练？”

先定位失败，比较 Prompt、检索、工具、流程设计和模型选择。只有当目标行为稳定且可衡量、存在合适数据、简单方法不能达标，并且生命周期收益足以抵消复杂度时，才考虑训练。详见[后训练指南](11-post-training.md)。

### “高管要求下周上线，但安全团队阻止，怎么办？”

既不能本能拒绝，也不能不安全地服从。识别具体风险，提出更窄的只读或合成数据试点，保留必要控制，记录剩余风险和决策权限，并提供带后果说明的分阶段选项。

### “技术效果不错，但试点采用率很低，怎么办？”

重新观察工作流：系统是否增加步骤、威胁现有激励、出现时机不对、缺乏信任或解释，或解决了低优先级问题。按用户群分析使用，用真实案例访谈，调整流程和培训，并保留停止条件。

### “客户需求正在让产品碎片化，怎么处理？”

将需求划分为可复用基础能力、可配置策略、集成适配器和一次性行为。衡量出现频率和价值，识别底层任务，提出产品边界，并透明沟通取舍。

### “讲一次你的失败。”

选择一件有后果的案例。说明你负责什么、哪个假设失败、什么证据暴露了问题、如何立即处理、做了什么系统性改变，以及后续结果。不要把无关痛痒的成功包装成失败。

### “所有事情都很紧急时如何排序？”

按结果影响、风险降低、学习价值、依赖关系和可逆性排序。公开决策，与负责人对齐，并明确哪些工作不会做。

## 45 分钟 Case 时间安排

| 时间 | 候选人的动作 |
|---|---|
| 0–8 分钟 | 澄清用户、工作流、结果、基线、限制与失败边界 |
| 8–13 分钟 | 说明假设、成功指标与非目标 |
| 13–25 分钟 | 设计最小完整系统及备选方案 |
| 25–32 分钟 | 定义评估、安全、可观测性与人工控制 |
| 32–38 分钟 | 规划试点、采用、责任与回滚 |
| 38–43 分钟 | 讨论扩展、成本、可复用产品经验和停止条件 |
| 43–45 分钟 | 总结建议、最高风险和下一项决策 |

时间表只是保护栏，不是固定台词；应根据面试官信号调整。

## 行为故事清单

为以下每个主题准备一个具体故事：

- 从模糊问题中发现真正需求；
- 困难技术取舍；
- 生产事故或严重失败；
- 与客户或高管的意见分歧；
- 技术很好但采用不佳；
- 没有正式权力下的跨职能交付；
- 安全、隐私或治理限制；
- 从客户专用需求提炼可复用产品能力；
- 缩小、重构或停止项目的决定；
- 快速学习新领域。

每个故事都应写出基线、你的决策、备选方案、证据、结果和之后发生的变化。面试官通常会通过追问确认工作是否由你本人负责。

## 向团队提问

- 合同签署后，FDE 团队具体对什么客户结果负责？
- 当前大多数项目处于哪个部署成熟度等级？
- 最近一次一线经验改变核心产品是什么？
- 哪些责任由产品工程、解决方案、客户成功和客户自身承担？
- 团队如何评审可复用工作与客户专用工作？
- 什么证据决定项目扩大或停止？
- On-call、出差和生产支持预期是什么？
- 团队最难解决的是技术、集成、采用，还是组织问题？

## 面试官轻量评分表

按证据从 1（有限）到 4（强）评分，而不是按表达魅力评分：

| 维度 | 强信号 |
|---|---|
| 需求发现 | 在提出功能之前找到真实工作流和限制 |
| 工程能力 | 能够实现并调试完整链路 |
| AI 评估 | 使用代表性证据并理解概率性失败 |
| 生产判断 | 设计控制、可观测性、可靠性和回滚 |
| 产品判断 | 缩小范围并明确取舍 |
| 客户信任 | 倾听、解释、建设性反对并管理预期 |
| 结果导向 | 将系统行为连接到采用和运营影响 |
| 学习复利 | 把一线证据转化为可复用产品改进 |

不要用单一平均分掩盖关键缺口：诚信、生产安全或动手工程能力上的严重不足，可能直接不符合岗位要求。
