# Forward Deployed Engineer 常见问题与术语表

**语言：** 简体中文 · [English](../en/14-faq-glossary.md)  
**内容类型：** 作者总结，并链接至带来源的详细章节  
**最近审阅：** 2026-10-22

## 快速结论

Forward Deployed Engineer（FDE）负责把一个模糊的客户问题，推进为真正被采用、成果可衡量的生产系统。不同公司使用的岗位名称并不统一，因此比较 FDE、FDSE、Applied AI、解决方案和部署岗位时，可靠方法不是只看 Title，而是检查它是否真正负责需求发现、实现、生产运营、用户采用，以及从一线回流产品的学习闭环。

本页提供简明回答和统一术语。岗位定义背后的证据见 [FDE 基础](01-fundamentals.md)、[岗位地图](02-role-map.md)和带核验日期的[官方资料目录](../../resources/official-sources.md)。

## 常见问题

### 什么是 Forward Deployed Engineer？

FDE 负责把一个模糊但高价值的客户问题，推进为真正被采用、成果可衡量的生产系统。这个角色通常结合问题定义、亲手构建、评测、生产上线、用户采用，以及把一线证据转化为可复用产品能力。这是本手册的工作定义，而不是放之四海而皆准的岗位说明。

### FDE 和 FDSE 是同一个岗位吗？

不一定。Forward Deployed Engineer（FDE）、Forward Deployed Software Engineer（FDSE）、Deployment Lead、Applied AI 及其他相邻岗位存在重叠，但不能直接互换。FDSE 往往更偏代码和架构；FDE 可能更明确地覆盖需求发现、工作流、采用和结果责任。具体职责比职位名称更重要。

### FDE 与软件工程师、解决方案架构师或顾问有什么区别？

关键区别是端到端的结果责任。软件工程师通常以产品能力为中心，解决方案架构师以目标架构为中心，顾问以分析或转型建议为中心；FDE 通常持续参与需求发现、实现、部署、采用和可复用经验沉淀，但具体边界因公司而异。详细比较见[岗位地图](02-role-map.md)。

### AI FDE 实际会构建什么？

常见工作包括数据与身份集成、检索系统、LLM 与 Agent 工作流、工具接口、用户界面、评测集、可观测性、批准机制、安全边界、部署基础设施和运行手册。正确答案可能是一个范围明确的决策支持流程，而不一定是完全自主的 Agent。

### AI FDE 需要哪些能力？

通常包括端到端软件工程、AI 与 LLM 系统设计、评测、生产可靠性与安全、数据和系统集成、产品判断、客户需求发现、技术与高管沟通、用户采用和业务价值分析。能力应通过真实交付证据体现，而不是依靠宽泛的自我描述。详细标准见[能力矩阵](04-skills-matrix.md)。

### FDE 一定要构建自主 Agent 吗？

不需要。合适的自主程度取决于后果、可逆性、可检测性、权限和评测覆盖。检索、内容起草、决策支持或经明确批准后执行，往往能以更低风险创造更大价值。只有在证据和控制措施充分时，系统才应获得更高权限。

### 什么时候应该使用 RAG、工具、微调或后训练？

应选择能解决已定位失败的最小干预。系统缺少不断变化或专有知识时使用检索；需要观察或改变外部状态时使用工具；失败源于运营流程时先改工作流或界面；只有当目标行为稳定且可衡量、存在合适数据、较简单方法无法达到目标，并且长期收益足以覆盖额外复杂度时，才考虑后训练。详见[后训练决策指南](11-post-training.md)。

### 如何避免形成永久的客户专用代码分叉？

把系统划分为可复用核心、受支持的配置层和客户边缘层。每个定制组件都必须做出明确决策：上游合并、转为正式配置、本地维护，或者按计划下线。重复出现的例外是产品证据，不应成为无限积累分叉代码的理由。

### 应该如何准备 FDE 面试？

准备完整交付闭环的证据：如何定义模糊工作流、构建最小完整系统、进行评测、处理可靠性与安全、推动采用、衡量结果，再把经验抽象为可复用能力。面试通常会同时考察编码与系统能力，以及客户、产品、取舍和部署案例。可使用[职业与面试指南](12-career-interview.md)和 [30/60/90 天学习路线](13-learning-path.md)。

### FDE 岗位需要多少出差？

行业没有统一数字。[官方资料目录](../../resources/official-sources.md)收录的当前招聘页从未注明固定比例到需要大量出差不等，具体要求会随公司、地区、级别、客户和季度变化。任何比例都只能用于对应岗位，做决定前应核实实时招聘页。

### 这份手册适合谁？

适合 FDE、FDSE、Applied AI 工程师、AI 产品构建者、解决方案工程师、Deployment Lead、技术顾问、求职者、招聘负责人、产品负责人，以及参与生产级 AI 落地的 GTM 团队。

## 术语表

| 术语 | 本手册中的定义 |
|---|---|
| **Forward Deployed Engineer（FDE）** | 负责把模糊客户问题推进为被采用、成果可衡量的生产系统。中文常见译法包括“前线部署工程师”“前向部署工程师”等，目前没有完全统一的标准译名。 |
| **Forward Deployment Engineer** | 有时用于相近工作的搜索词或职位变体；不能只凭写法推断职责。 |
| **Forward Deployed Software Engineer（FDSE）** | 通常更偏代码与架构的一类前线部署岗位，具体边界因公司而异。 |
| **Deployment Lead** | 通常更聚焦工作流梳理、项目执行、上线准备、组织变革和采用，是多职能部署团队中的一种角色。 |
| **Applied AI Engineer** | 围绕 AI 能力构建产品或客户工作流；当它直接负责结果和部署时，与 FDE 高度重叠。 |
| **Solutions Engineer** | 帮助客户评估、集成或采用产品；可能与 FDE 重叠，但不一定负责完整的生产和学习闭环。 |
| **Solutions Architect** | 设计目标方案和集成架构；实现与采用责任因组织而异。 |
| **Customer Engineer** | 客户侧技术岗位，范围可能从售前赋能延伸到亲手实现和生产支持。 |
| **Forward deployment** | 深入用户及其环境，构建、上线、衡量并持续改善真实运营结果。 |
| **Outcome contract / 结果契约** | 对用户、流程、基线、目标、约束、失败边界、负责人和退出条件的共同约定。 |
| **Thin vertical slice / 薄而完整的垂直切片** | 使用真实关键数据、集成、权限和控制措施的最小端到端系统。 |
| **Evaluation set / 评测集** | 用于比较系统行为并发现回归的代表性案例和验收规则。 |
| **Trace / 调用链记录** | 用于调试和审计的模型、上下文、检索、工具、策略及流程事件记录。 |
| **Observability / 可观测性** | 基于证据理解系统、模型、用户和业务行为的能力。 |
| **Autonomy ladder / 自主程度阶梯** | 只有当风险控制和证据充分时才逐步提升系统权限的 A0–A5 分级。 |
| **Adaptation boundary / 适配边界** | 可复用核心、受支持配置与客户特定边缘之间的边界。 |
| **Post-training / 后训练** | 预训练后的权重更新，包括监督微调、偏好优化和强化学习。 |
| **Field-to-product learning / 一线到产品的学习闭环** | 把部署证据转化为可复用的产品、模型、平台、评测与文档改进。 |
| **Adoption / 用户采用** | 系统成为真实工作流中的持续使用方式，而不是初期热情或一次验收。 |
| **Runbook / 运行手册** | 记录日常运行、升级、事故、责任与恢复方式的操作手册。 |
| **Rollback / 回滚** | 失败后恢复到已知更安全版本或工作方式的经过测试的路径。 |
| **FIELD Framework / FIELD 框架** | Bosheng Ding 原创的定义、观测、构建、上线与提炼闭环：Frame、Instrument、Engineer、Launch、Distill。 |
| **FDE Delivery Maturity Model / FDE 交付成熟度模型** | Bosheng Ding 原创的 L0–L5 模型，用来区分演示、有用、可运营、被采用和形成复利的系统。 |

## 归属与适用边界

**FIELD 框架**与 **FDE 交付成熟度模型**是 Bosheng Ding 的原创总结，并非行业标准。公司岗位描述是基于一手资料、带日期的观察。术语表只统一本手册内部用法，并不声称整个行业拥有固定分类。引用原创框架时请使用 [CITATION.cff](../../CITATION.cff)。
